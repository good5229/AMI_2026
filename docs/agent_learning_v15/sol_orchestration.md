## Methodological Relevance

The harness guidance treats repository knowledge, executable checks, and feedback loops as the system of record. v0.15 therefore encodes overlap, source provenance, same-threshold, deterministic assignment, and claim boundaries as machine-checkable artifacts rather than relying on narrative assurances. Multi-agent work is split into disjoint methodology, statistics, runtime-audit, implementation, and final-red-team scopes.

## Risks

- Reusing v0.10 meter-days would turn an old evaluation pool into hidden tuning data.
- Ablating documented but runtime-inactive inputs would manufacture mechanism importance.
- Reoptimizing each variant would compare new detectors instead of H1 component necessity.
- Repeated injections within a meter-day would create pseudoreplication.
- Unlabeled natural background density could be mislabeled as FPR or specificity.
- Strong target-domain results could erase the negative v0.13/v0.14 cross-domain evidence.

## Adopted Rules

1. Freeze predecessor files and exact H1 config hashes before new pair construction or outcome evaluation.
2. Select the remaining pool without H1 actions or scores and require zero v0.10/canonical-buffer overlap.
3. Assign at most one anomaly or benign operator per meter-day using a frozen namespace and balanced deterministic allocation.
4. Ablate only code-confirmed runtime-active components and preserve the Full H1 operational threshold for every variant.
5. Use paired results at the counterfactual pair level and meter-day cluster statistics with preregistered Holm correction.
6. Report weak, null, adverse, unavailable, and non-comparable results without variant shopping.
7. Keep target-domain counterfactual contribution separate from real field accuracy, real-background FPR, fault probability, and general electrical anomaly performance.
8. Require independent LUNA QA plus full Flutter analyze, test, Web release, and Android release before commit or push.
